### D18 · Django super admin (ADR, P5.1)

**Context.** Autofix had a small super admin inside the Next.js app (P4.5: garages list, plan and status, read-only "View as support", job health). Temitope asked for one that replicates the Vitalos platform Super Admin (`vitalos-platform/superadmin`, ADR-026): a Python service with its own sign-in, roles, TOTP, audit trail, REST API and the same look, covering every garage.

**Decision.** `superadmin/` is a Django 5.2 LTS app on the reference's stack and layout (Python 3.12, HTMX 2, Tailwind v4 standalone CLI, PostgreSQL 17, simple-history, axes, django-otp, django-csp, DRF + drf-spectacular, WhiteNoise, gunicorn; `apps/<name>/services.py` for writes and `selectors.py` for reads). It has two databases:

- `default`: its own Postgres (users, OTP devices, sessions, axes, history, notifications, its append-only audit trail).
- `autofix`: Autofix's Supabase Postgres as the role `autofix_superadmin` (migration `20261028004000_superadmin_role.sql`). The role reads only schema `superadmin`, a set of views over the tables it needs with contact details and registrations masked in the database and no message bodies, payloads or token hashes. Sessions start read-only. Django maps the views with unmanaged models; `AutofixRouter` never migrates or writes that alias, the models refuse writes, and `migrate --database autofix` is refused.

Writes never bypass Autofix's rules: the role can EXECUTE exactly `platform_update_garage`, `platform_retry_job` and the new `platform_request_domains_check` (which only queues Autofix's own `domains.check` job). For each change Django opens a read-write transaction, sets `request.jwt.claims` to the signed-in person's linked platform admin with `aal2` (Django has just verified their TOTP), and calls the function, which re-checks `platform_admins`, validates the reason and writes `platform_audit_log` and the garage's `admin_audit_log`. Nothing touches bookings. "View as support" is an audited POST that redirects to the garage in Autofix's `/admin`, where the read-only session starts under the admin's own Autofix sign-in and MFA (no credentials in the URL; ADR-044 "Open" pattern). The super admin serves the ADR-044 product status at `GET /api/platform/v1/status` for the Vitalos Product Pipeline.

**Options considered.** (1) Grant the role `BYPASSRLS` and SELECT on public tables: rejected, it would see every column (phones, bodies, payloads) and creating BYPASSRLS roles is not portable on hosted Supabase. (2) RLS policies `to autofix_superadmin using (true)`: rejected, it breaks the tenancy suite's rule that every policy is scoped by `current_garage_id()`, and still exposes every column. (3) Call `/api/platform/*` over HTTP: impossible without a Supabase user session and AAL2 token for each Django user. (4) New `superadmin_*` wrapper functions that take an actor id: more SQL to maintain for the same checks; the claims approach calls the existing functions unchanged.

**Consequences.** The role can act as any user listed in `platform_admins`, but only through three functions that each require that membership; its password is the key and lives only in the platform's secret store. Django's TOTP stands in for Supabase AAL2 on these calls. Each Vitalos user who should change anything needs an Autofix platform admin and a link (Settings → Users); without one Autofix is read-only for them. Two super admins exist until the Next.js one is retired.

**Address: a path, not a subdomain (Temitope, 28 Oct 2026: "I prefer the path, but build a solid security for it").** The super admin is served at `https://autofix.vitalos.co.uk/superadmin`. The container keeps its own origin; `src/proxy.ts` forwards `/superadmin/*` on the admin host to it (`SUPERADMIN_ORIGIN`), so no DNS change is needed. Sharing an origin with the Autofix app is the cost of the path (script on one path can drive the other), so the security is built around that:

1. **Only the proxy reaches the app.** Every forwarded request carries `SUPERADMIN_PROXY_SECRET` in `x-autofix-superadmin-proxy`; the container compares it in constant time and answers anything else (including its own address, any path outside `/superadmin`) with a bare 404. Only `/healthz/` answers without it. The secret is removed from the request before logging.
2. **Trusted proxy headers only behind the gate.** The proxy drops any `x-autofix-superadmin-*` header the browser sent and sets the client IP (Vercel's `x-real-ip`, used for sign-in lockouts and the audit trail) and public host (CSRF origin checks).
3. **Cookie isolation both ways.** The super admin's cookies are `__Secure-afsa_*`, `Path=/superadmin/`, `HttpOnly`, `Secure`, `SameSite=Strict`, so the Autofix app never receives them; the proxy forwards only those cookies, so Autofix's Supabase session never reaches the super admin.
4. **A fresh second factor per sensitive action.** TOTP is required for every role at sign-in, and each change to Autofix (plan/status, bulk status, job retry, domain re-check), each personal-data view (customer details, View as support), each user change and each API token needs a new authenticator code with the request (django-otp refuses a reused code and throttles failures). A script on the origin cannot produce one.
5. **Its own headers.** The proxy leaves the Django response alone: strict nonce CSP with `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`, `X-Robots-Tag: noindex`, `Cache-Control: private, no-store` on every page; `next.config.ts` skips `/superadmin` for its own headers and trailing-slash redirect.
6. **Proved in CI.** The Super Admin workflow runs the production image in path mode and checks the gate (404 without or with a wrong secret) before the browser smoke test and axe run through `/superadmin`; `src/__tests__/superadmin-proxy.test.ts` covers the proxy.

Residual risk: a script running on `autofix.vitalos.co.uk` (an XSS in the Autofix app) could read pages a signed-in super admin can see, but not change anything, see personal data or mint tokens without a fresh code; the same script could already act as that person in Autofix's own `/admin`. A subdomain would remove this; it stays a one-setting change (`SUPERADMIN_PATH_PREFIX` empty plus DNS) if Temitope wants it later.
